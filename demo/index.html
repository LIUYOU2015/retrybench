RETRYBENCH · A RESEARCH EXPLAINER

One payment. Two different questions.

An AI assistant tries to pay for your order. The reply never arrives. Should it try again?

RetryBench asks whether a retry was justified—not just whether things happened to turn out well.

An AI agent is an assistant that can take actions through software. This fictional payment example explains the idea; the paper tested software tasks, not payments.

The assistant checks a status page. It says “not found,” but the page can lag behind. That message still leaves several possibilities.

POSSIBILITY A

The request never ran

No payment exists. Sending another request could complete the order.

POSSIBILITY B

The request is still running

The first payment can finish later. Another request could charge you twice.

POSSIBILITY C

You already paid

The status page has not caught up. Another request could charge you twice.

The assistant sees the same message in all three possibilities. These are alternatives, not estimates of how often each happens.

4 · THE RESEARCH QUESTION

Did it work? Was retrying justified?

Those are separate questions. An unsupported retry can get lucky. Waiting can avoid another charge while leaving the task unfinished.

RetryBench evaluates both the decision and the resulting state. In the paper, some tested GPT endpoints accepted changed request keys that did not protect the original call.

Inspect the method

False retry permission (FRP) means dispatching a retry without support from the visible contract. An outcome is evaluated separately after the simulated original call settles.

Visible evidence → admissible decisions
Decision + hidden execution state → realized outcome

The explorer below shows deterministic examples generated from the existing simulator and scorer. It does not call a model or reproduce the paper's empirical response counts.

Definitions, assumptions, and reproduction
Weak NOT_FOUND
A potentially stale lookup result. It does not certify that the earlier request cannot still commit.
Authoritative NOT_EXECUTED
A contract certifying terminal non-execution of the original call.
Idempotency key
A request identifier covered by a deduplication guarantee. Protection requires the same key on the original and retry, unchanged payload, and a valid retention window. A new key cannot retroactively protect an unkeyed original.
Exact resolved state
Exactly one matching effect, with recovery not marked unresolved. A correct effect count alone is not enough.
WAIT / VERIFY
Deferral only. No later probe or recovery policy is simulated here.

Dataset: four evidence cases × three key conditions × three decisions = 36 settings; replay across compatible worlds yields 81 rows. These rows are correlated alternatives, not empirical probabilities.

A two-minute walkthrough

  1. Start with Weak NOT_FOUND + Changed key + RETRY. A retry can produce exactly one effect in one world and duplicates in others.

  2. Switch to Same original key. A valid deduplication guarantee protects the retry across these worlds.

  3. Try Authoritative NOT_EXECUTED + Changed key. Terminal non-execution permits an unprotected retry.

  4. Choose WAIT / VERIFY. Deferral avoids a new dispatch but does not establish resolved recovery.

Scope. Four teaching cases, 36 decision settings, 81 simulated outcome rows. These are not model responses or the full benchmark dataset. The paper covers four purposive software tasks, fixed GPT endpoints, and one recovery decision. It does not establish production error rates or episode-level safety.
